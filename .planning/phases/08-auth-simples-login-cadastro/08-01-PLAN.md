<threat_model>
Trust boundaries:
- Browser form input is untrusted.
- API validates all auth input server-side.
- Database stores password hashes only.
- Session token lives in HTTP-only cookie, not frontend JS.

STRIDE register:
- S-01 spoofing login by brute force: mitigate with `@fastify/rate-limit` on login/register.
- T-01 tampered request body: mitigate with Zod schemas and strict field parsing.
- I-01 password hash exposure: mitigate with Argon2id hashing and never selecting/returning `passwordHash` in response DTOs.
- I-02 user enumeration: mitigate login with generic `Email ou senha invalidos`.
- E-01 forged auth cookie: mitigate JWT signing with `JWT_SECRET` length validation and `httpOnly`/`sameSite`/`secure` cookie flags.

Block on: high.
</threat_model>

- email lowercase.
- birthDate valid and not future.
- password min 8, max 128, all characters allowed.
- confirmPassword must equal password.
Create session helpers to sign/read JWT from HTTP-only cookie.
Create routes:
- `POST /api/auth/register`
- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/auth/me`
Register `@fastify/cookie`, `@fastify/rate-limit`, `@fastify/jwt`, and `registerAuthRoutes` in `apps/api/src/index.ts`.
Rate limits:
- login: max 5 per minute per IP/email key when possible.
- register: max 3 per 5 minutes per IP.
Responses:
- success user DTO excludes `passwordHash`.
- login failure returns generic 401.
- validation failure returns structured field errors.
- rate limit returns 429 with retry info.
